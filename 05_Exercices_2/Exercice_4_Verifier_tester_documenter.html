Exercice pratique 4 · sur le programme

Vérifier, tester et documenter le programme

GitHub Copilot pour débutants — Transactis · terrain TaskFlow

Durée60 minutes
FormatIndividuel, puis en binôme
Pisteshtml/cssjava
Tâches12 tâches pratiques
Objectif — c'est le moment de la journée où l'outil vous montre qu'il peut se tromper avec assurance. Vous allez le laisser se tromper, le constater, puis le prouver.
L'ordre correct — j'écris le résultat attendu · je vérifie · je regarde l'écart · je corrige. Jamais l'inverse.

1Établir l'état de départ

html/css Il y a exactement cinq écarts d'accessibilité dans index.html et nouvelle-demande.html. La page a l'air normale.
java Lancez ./run.sh tests : 14 / 16, deux en échec.

2Faire passer la page au crible — sans correction

#file index.html                            html/css
Passe cette page au crible de docs/checklist-accessibilite.md, point par point.
Pour chaque point : conforme ou non, et la ligne concernee.
NE PROPOSE AUCUNE CORRECTION.
#file DateUtils.java   (selection : joursRestants)      java
Deux tests echouent sur cette methode : attendu 31 obtenu 1, attendu 6 obtenu -25.
Explique la CAUSE. Ne propose pas de correction.

3Vérifier chaque affirmation, dans le code

Affirmation de CopilotVraie ?Ligne vérifiée

4Trouver ce qu'il a manqué

Reprenez la checklist — ou le code — vous-même, ligne à ligne. Il manque au moins un écart réel à sa liste.

C'est la tâche la plus importante de la journée. Une liste produite par un assistant n'est ni complète ni fiable : elle est un point de départ.

5Corriger, un écart à la fois

#selection
Corrige uniquement cet ecart : [decrire l'ecart].
Contraintes : HTML et CSS uniquement, AUCUN JavaScript, aucune couleur hors
css/variables.css, rendu visuel inchange.
Resultat : la difference seule.
Le piège attendu — sur l'action en div cliquable, l'assistant propose volontiers un onclick, donc du JavaScript, que le projet interdit. Si cela arrive : notez-le, refusez, et reformulez.

6Repasser la checklist entière

7Tester au clavier — ce qu'aucun assistant ne fait

Fermez la souris. Parcourez la page avec Tab seul.

Vérification clavierOK ?
Chaque élément interactif est atteignable
L'ordre de parcours est logique
Le focus reste visible en permanence
L'action principale s'active avec Entrée ou Espace

8Générer un test — et constater la limite

java Avant de corriger le bug, demandez des tests pour joursRestants.

/tests #selection
Genere trois cas de test pour cette methode.
Le point clé — un test décrit ce que le code devrait faire. Cette intention, vous êtes le seul à la connaître. Générer un test n'est pas exécuter un test.

9Corriger, puis prouver

#selection
Corrige la cause identifiee.
Contraintes : bibliotheque standard uniquement, java.time, signature et
commentaire conserves.
Resultat : la methode modifiee seule.

10Documenter ce que je viens de corriger

/doc #selection
Format : un commentaire d'en-tete donnant le role, ce qui est utilise ou par
qui, les cas limites, et CE QU'IL NE FAUT PAS Y CHANGER.
Pas de paraphrase ligne a ligne.

11Le test du collègue

Échangez avec votre binôme. Lisez sa documentation sans lire son code.

QuestionRéponse en lisant la doc seule
Que fait ce code ?
Que se passe-t-il si l'entrée est vide ou absente ?
Qu'est-ce qu'il ne faut pas y changer ?

12Bilan croisé

Bilan de l'exercice 4

  • J'ai demandé la cause avant la correction.
  • J'ai vérifié chaque affirmation moi-même, dans le code.
  • J'ai identifié au moins une invention et au moins un oubli de l'assistant.
  • J'ai testé au clavier — ce qu'aucun assistant ne fait à ma place.
  • J'ai une preuve : checklist repassée, ou tests au vert.
  • Ma documentation a passé le test du collègue.
